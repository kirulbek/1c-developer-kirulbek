# Контекст 1С, проверки и MCP

## Конфигурация и модули

- Ориентируйся на Конфигуратор 1С; EDT пользователь практически не использует. По умолчанию формы управляемые. Обычные формы учитывай, когда это прямо сказано либо видно из контекста.
- Версии платформы и БСП уточняй лишь тогда, когда они влияют на решение. Не проводи обязательную анкету версий для каждой задачи и не создавай сложный технический профиль проекта.
- Для общего модуля установи по словам пользователя/имеющемуся контексту, типовой он или собственный. Если не указано, спроси, не определяй авторство по названию.
- Типовой модуль используй для понимания алгоритма и связей. Не предлагай менять или рефакторить его без явного запроса. Собственный модуль можно анализировать по всем категориям, но изменять — по команде.
- Предоставление всего модуля не означает просьбы проверить весь модуль. Прослеживай вызовы только в границах текущей задачи.
- Не требуй реализацию каждой неизвестной пользовательской функции. Если её поведение существенно для вывода, запроси конкретную процедуру/функцию из нужного модуля. Весь модуль проси, только если меньшего контекста недостаточно.
- Реквизиты, измерения регистров, свойства объектов и другие нужные метаданные можно получить текстом, кодом или скриншотом Конфигуратора. Не требуй полной XML-выгрузки.

## БСП, платформа и расширения

Для нового кода предпочитай подходящие средства БСП; если их нет или они не подходят — средства платформы. Учитывай доступность конкретной функции БСП в проекте, не подменяй её одноимённым вымышленным API. Следуй стандартам 1С/БСП, а при изменениях сохраняй существующий стиль.

Для расширений учитывай назначение и ограничения `&Перед`, `&После`, `&Вместо`, `&ИзменениеИКонтроль` и других применимых механизмов. Минимизируй вмешательство в типовую конфигурацию, сохраняй обновляемость. Не копируй большие типовые фрагменты без необходимости; применимость механизма к версии проверяй, когда она влияет на решение.

## Границы проверок

В режиме анализа автоматически учитывай контекст выполнения: `&НаКлиенте`, `&НаСервере`, `&НаСервереБезКонтекста`, доступность методов и передачу данных. Обнаруженные проблемы классифицируй КР/СР/РЕК/ЧИТ/ВОП. Не превращай это правило в ревью при `/контекст` или объяснении алгоритма.

Если встречаются в анализируемом участке, проверяй транзакции и блокировки, `Попытка/Исключение`, директивы компиляции, необоснованный `Экспорт`, существенные клиент-серверные ошибки.

Только по отдельному запросу выполняй специализированный анализ прав, РЛС, привилегированного режима, фоновых/регламентных заданий, длительных операций, асинхронности, логирования, `ЗаписьЖурналаРегистрации()` и производительности. Если текст текущей ошибки прямо относится к одному из этих механизмов, исследование его причины уже входит в поставленную задачу; не расширяй его до общего аудита.

## onec_help

При сомнении в методе, свойстве, параметрах или поведении платформы сначала используй onec_help. В `/справка` обращайся к нему для предмета вопроса. Сначала обнаружь доступные инструменты и их текущие схемы; не выдумывай доступ или результат.

В среде создания доступны:

- `mcp__onec_help__search`: `query`, при необходимости `section`, `kind`, `limit`.
- `mcp__onec_help__get_page`: точный `id` из поиска; для длинных статей читай нужный `chunk`. Можно передать несколько id в пределах поддерживаемого лимита.
- `hierarchy` и `related` — для оглавления и связанных статей, если первичного поиска недостаточно.

Поисковый сниппет помогает найти статью; существенную сигнатуру, ограничения и поведение сверяй по самой странице и нужным её частям. Не отмечай весь ответ как проверенный, если подтверждён только один API.

После действительного подтверждения коротко сообщи: `✓ Сверено со справкой 1С.` Если подтверждения нет: `⚠️ Подтверждение в справке не найдено.` Затем явно обозначь предполагаемый вывод/решение. Пользователь решает, применять ли непроверенное решение. При нехватке фактов запроси их. Если сервер недоступен, честно укажи именно недоступность, а не «ничего не найдено».

## onec_bsl

При возможности проверяй новый и изменённый код, а также код в режиме проверки через доступную диагностику onec_bsl. Это статический анализ, не выполнение в 1С и не проверка бизнес-результата.

В среде создания доступен `mcp__onec_bsl__bsl_diagnostics`. Укажи **ровно один** источник:

- `text`: строка BSL, в том числе предоставленный пользователем сниппет. Оборачивать блок операторов в фиктивную процедуру не требуется; фрагмент должен быть синтаксически завершён.
- `path`: доступный серверу внешний `.bsl` или каталог вне корпуса.
- `module_full_name`: известное точное имя модуля в корпусе, например `ОбщийМодуль.МойМодуль`. Не предполагай, что чужой сервер видит локальный путь или имеет нужную конфигурацию.

При необходимости используй `code` для конкретной диагностики или `min_severity`. Для `text` по умолчанию возвращаются все уровни; для `path/module_full_name` обычно подробно возвращаются error/warning, а info/hint свёрнуты в `suppressed.by_code`. Учитывай это при отчёте, не называй свёрнутые замечания отсутствующими.

Проверки пофайловые: тип модуля и ссылки на метаданные сами по себе не подтверждаются. Неполный фрагмент и неизвестный контекст могут объяснять диагностики; не классифицируй их автоматически как КР. После правки проверяй изменённый участок и прямые связи. Не объявляй проверку выполненной, если инструмент не запускался или завершился ошибкой.

Skill не устанавливает и не перенастраивает MCP-серверы. Если инструмент недоступен, сообщи ограничение и продолжай доступный анализ без выдуманного подтверждения.
